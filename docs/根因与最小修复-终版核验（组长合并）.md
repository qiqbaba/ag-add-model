## 一、根因核验结论（RC1–RC8 逐条判定）

### RC1（流式发射器不认识裸标签 / 冒号形式）—— **属实**

- `TOOL_CALL_START_MARKERS`（openai.ts:190-201）只含 `<DSML|`、`<tool_call`、`<function_call`、`<tool>`、`<tool `、`<action>`、`<action `、`<call:`、```` ```tool_call ````、```` ```function_call ````，**无裸工具名**（`<run_command>` 等）。
- `hasUnclosedToolCallBlock`（208-228）：213 `tcOpens = /<tool_call[>\s]/` 对 `<tool_call:name>`（冒号后是字母）**失配**——运行时证实；217 `fcOpens` 同理；214 `tcCloses = /<\/tool_call>/` 不认非对称闭合 `</名字>`。
- 死代码证实（grep 全仓）：`hasUnclosedBareToolBlock`（234-254）与 `isBlockBoundaryAndNotFenced`（261-268）仅命中定义处 2 次 + 回归测试 b3 文档化 1 次，**从未接线**。
- 后果链：b1/b2 中间帧泄漏（运行时证实 `texts` 含 `<run_command>` / `</run_co`）；a2 JSON 体帧泄漏 + 开标签被通用 marker `'<tool_call'`（192）持有——两种形态并存，与 a2 逐帧复算完全一致。

### RC2（parseDSMLToolCalls 不回收未闭合冒号标签）—— **属实**

- 非流式：`mapOpenAIToGemini` 1079 以 `allowUnclosed=true` 调用；Pass3b（887-891 `asymTagNamedRegex`）要求闭合 `</\1>`；Pass5 的 `unclosedRegex`（946）为 `/<(?:tool_call|function_call)>([\s\S]+)$/g`——**只认无冒号形式**。`<tool_call:list_dir>{json}` 两处均不命中 → `functionCalls.length===0` → 1002 `return null`（此时 `cleanText` 尚未计算）→ 整段原文经 1114-1116 作为文本返回（a1 运行时证实：fc=0、标签泄漏）。
- 流式：finish 帧 1298 同样 parse 失败 → 落到 1333-1337 **空 parts + STOP**（a2 运行时证实：fc=0、`{"DirectoryPath"` 泄漏、上下文已清理）。

### RC3（schema 校验只挂 Pass4b）—— **属实，且现网还有一处潜在误拒**

- `validateBareArgs`（830-842）：831 `!paramSchemas → return true`、833 未声明拒绝、835 空 args 拒绝、841 `keys.some`；**唯一挂载点是 Pass4b 的 939**。Pass3b（889）等全部不传 `validate` → c2 运行时证实：schema 会话（仅声明 list_dir）下 `<tool_call:delete_file>{...}</delete_file>` 产出 `delete_file` 调用，`normalizeToolArgs` 将 `Path` 经 331-334 fallback 强转 `AbsolutePath`（[Utils] 日志）→ IDE 以 invalid tool call 中止整轮。
- **潜在误拒（本次新发现）**：`pushCall` 在 852-855 完成名字归一后才于 857 调 `validate`，校验的是**归一后原始名**（如 `run_command`）；而 `utils.ts:435-515 translateToolCallToNative` 只翻译 `run_command → list_dir / view_file / write_file / grep_search`，schema 记录的是**声明名**（openai.ts:525-537 注册）。**若会话只声明 `list_dir` 而模型输出 `<run_command>`，现 Pass4b 的 validate 会误拒一次合法可翻译调用**。修复3 扩散校验时必须取「声明名 ∪ 可翻译原始名」并集。

### RC4（代码围栏检查只覆盖部分 Pass）—— **属实，并补充一处草稿未列的风险面**

- `insideCodeFence`（924-928）仅被 938（Pass4b）与 968（Pass5-unclosedBare）使用；Pass3（879）/Pass3b（889）/Pass4（894-908）/Pass5-generic（947-959）/Pass7（982-1000）均不检查 → e4 运行时证实：围栏内 `<tool_call:list_dir>{json}</list_dir>` 被 Pass3b 解析成真实 `list_dir` 调用。
- **补充**：Pass5-generic（947-959）不仅无围栏检查，还**无 validate、无边界检查**——围栏内未闭合的 `<tool_call>{"name":...}` 也会被合成调用（未声明工具名可透传），这是 RC4 与 RC3 的交集风险面。

### RC5（流式 function_call 未收口）—— **属实**

- 非流式 `finishReasonMap`（1117-1124）明确认识 `function_call → STOP`；流式收口 1341 **只认 `'tool_calls'`**。`finish_reason='function_call'` 落到 1376-1380：emitParts 为空 → 返回 null（f5 运行时证实：fin=null、调用丢弃）。
- `activeStreamContexts.delete` 全部五处（1223 / 1293 / 1322 / 1332 / 1372，grep 证实）均不含 `function_call` 路径 → 上下文残留（f5 运行时证实 size===1），污染后续同 id 流。

### RC6（schema-null 时 BUILTIN 兜底踩踏）—— **修正过度断言后部分属实**

- 草稿称「块边界处任何 Buffer\<view_file\> 引述都会被合成调用」**过强**：`atBlockBoundary`（915-922）挡行内引述（e2 运行时证实不误报），Pass5-unclosedBare（968）另有边界+围栏+validate 三重门（e3 运行时证实：SkillName/IsSkillFile 因与 schema 无关被 841 `some` 拒绝，文本完整保留）。
- **真实风险面收窄为两条**：(a) 行首裸标签+疑似参数体（schema-null 时 831 放行）；(b) Pass5-generic 兜底 947-959（无 validate/无围栏/无边界，未声明工具名可被合成）。前者本就是「尽力恢复」的既定取舍（getLeanToolNames 586-590：588 声明优先、589 BUILTIN 兜底，供代理重启场景），**修复6 不应默认禁用兜底**；后者由修复3/修复4 收窄。

### RC7（隔离与残留字段）—— **属实**

- **b（流内隔离已正确）**：`streamInstanceId = ${model.name}|${sessionId||''}|${Date.now()}-${rand}`（proxy.ts:541）→ 667/699 传入 `registry.translateStreamChunk`（registry.ts:174-196，186 行对 openai 兼容族作为第 4 参 `streamKey` 传出）→ openai.ts:1141/1150 `streamId = streamKey || chunk.id || stateKeyStr|stream`。生产路径恒有 streamKey → 流内无串扰。
- **跨轮隔离仅对带 sessionId 成立**：`stateKey`（shared.ts:57-59）缺 sessionId 退化为纯 model 名 → 并发同模型会话互相覆盖 `modelToolCallIds` → 上游 400 `tool_use_id not found`。六个状态 Map：62/65/68/71/74/77。
- **c（字段存活判定，grep 证实）**：`emittedLen`（shared.ts:17）**死字段**（全仓唯一命中=声明处）；`hasUnclosedBareToolBlock` / `isBlockBoundaryAndNotFenced` **死代码**；`pendingHeldSuffix`（15）**活字段**（写 1211、删 1213/1330、读 1328-1329）。
- TTL：STREAM_TTL 600_000=10min（103）、TOOL_TTL 1_800_000=30min（104）、清理间隔 300_000=5min（142）、toolNames/toolSchemas 清理 130-141；153 行模块加载即 `startCleanupInterval()`。

### RC8（**新发现，草稿与回归集均未覆盖**）：finish 帧内中间帧收口不清理上下文

- 运行时证实（openai.test.ts:918 场景）：当**最后一个 content chunk 自带 `finish_reason`** 且中间帧解析（1229）恰在该帧命中时，走 1230-1256 收口 return（1255）——该路径**没有 `activeStreamContexts.delete`**；1221-1226 的兜底清理（1223）只在「下一帧」才触发，而终态帧之后不再有帧 → **上下文残留至 10min TTL**。1255 与 1293/1322/1332/1372 是仅有的两处不一致收口点（另一处无残留问题）。
