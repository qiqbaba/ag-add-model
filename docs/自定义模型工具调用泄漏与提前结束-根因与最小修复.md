## 一、结论摘要

**两个症状、六条根因，全部可定位到 `src/proxy/translators/openai.ts` 的流式发射逻辑与 `parseDSMLToolCalls` 的各 Pass 正则。**

- **Symptom A（裸标签 / 工具标签漏走流）**：流式发射器只“认得” `TOOL_CALL_START_MARKERS`（190-201）里的标签与 `hasUnclosedToolCallBlock`（208-228）里被计数的开闭对；**对裸标签（`<run_command>` 等）与非对称冒号形式（`<tool_call:name>`）都不认**，于是中间 chunk 把这些内容当普通可见文本透出。**根因 G6 + G2**。
- **Symptom B（提前 STOP / 合成伪调用致中断）**：两条路径：
  1. `parseDSMLToolCalls` 对 **未闭合的非对称冒号标签**（Pass5 的 `unclosedRegex` 只认 `<tool_call>` 无冒号、见 946）与 **未声明工具名**（`validateBareArgs` 只挂在 Pass4b，见 939）解析失败 → 返回 `null`（1002）→ finish 分支（1258-1338）**以 `STOP`（1335）+ 泄漏文本收尾**，IDE 以为模型“说完了”，不执行工具。**根因 G1 + G3**。
  2. `validateBareArgs`（830-842）用 `some()`（841）、schema 为 null 时直接放行（831），且 Pass3/3b/4/7 完全不做 schema / 代码围栏校验 → 把**正文提及或围栏引用**合成一个真实 `functionCall`（未声明工具 / 参数强转），IDE 收到 `invalid tool call` 后**中止整轮**。**根因 G3 + G4**。
- 另有一条独立 bug（**G5**）：流式 `finish_reason='function_call'` 不进入 native 工具调用收口（只有 `'tool_calls'` 走 1341），导致累计的 `delta.tool_calls` 被丢弃，且 `activeStreamContexts` 不清理（污染后续同一 id 流）。

## 三、根因分析（编号，引用精确行号）

### RC1（＝G2/G6）流式发射器不认识裸标签 / 冒号形式 —— Symptom A 主根因

`mapOpenAIChunkToGemini` 的发射判定（1179-1218）：

```ts
1179  const alreadyInsideToolBlock = hasUnclosedToolCallBlock(prevAcc);
1186  let earliestIdx = -1;
1187  for (const marker of TOOL_CALL_START_MARKERS) {
1188    const idx = text.indexOf(marker);
...
1194  let safePrefix = earliestIdx >= 0 ? text.slice(0, earliestIdx) : text; // ← 无 marker 时整段当正文
```

- `TOOL_CALL_START_MARKERS`（190-201）只含 `<DSML|`、`<tool_call`、`<function_call`、`<tool>`、`<tool `、`<action>`、`<action `、`<call:`、`````tool_call````、`````function_call````。**没有裸工具名**（`<run_command>`、`<view_file>`、`<list_dir>`、`<grep_search>`…）。
- `hasUnclosedToolCallBlock`（208-228）只按 `DSML|`、`<tool_call[>\s]`（213）、`<function_call[>\s]`（217）开闭计数，外加 `<call:`（223）。**既不认 `<tool_call:name>`（213 的 `[>\s]` 在 `:` 处失配），也不认裸标签**。
- 结果：中间 chunk 携带 `<run_command>{...}` 时，`earliestIdx===-1`（1194）→ 整段当作 `safePrefix` 透出。**根因是**：本应承担扣留职责的 `hasUnclosedBareToolBlock`（234-254）与 `isBlockBoundaryAndNotFenced`（261-268）**已定义但从未被接线**（全仓库 grep 仅命中其定义处与 b3 测试），这正是 subtask 4 判定的 **G6**。

> 注意“叠加”关系：裸标签若最终能闭合且工具名已声明，**中间帧泄漏后仍能在收口 parse（1229）解析出 functionCall**，所以调用“没丢”，但泄漏面在中间帧（b1 注释）。若不能解析（见 RC2/RC3），则既泄漏又丢调用（Symptom B）。

### RC2（＝G1）`parseDSMLToolCalls` 不回收未闭合的冒号非对称标签 —— Symptom B 主根因

- **非流式**（`mapOpenAIToGemini` 1079 传 `allowUnclosed=true`）：Pass3b（887-891）要求存在闭合 `</\1>`；Pass5 的 `unclosedRegex` 是 `/<(?:tool_call|function_call)>([\s\S]+)$/g`（946）——**只匹配无冒号的 `<tool_call>` / `<function_call>`**。`<tool_call:list_dir>{json}`（无闭合）两处都不命中 → `functionCalls.length===0`（1002）→ **返回 null，整段原文经 1114-1132 作为文本返回**（泄漏 + 无调用）。
- **流式**：开标签 `<tool_call:list_dir>` 因命中通用 marker `'<tool_call'`（192）而被扣留；但 `hasUnclosedToolCallBlock`（213）不认冒号 → `alreadyInsideToolBlock`（1179）为 false → **后续 JSON 体帧当普通正文放行**（1194）。finish 时 `allowUnclosed=true` 的 parse（1298）仍因 946 不认冒号而返回 null → 回到 1333-1337 输出**空 parts + STOP**（提前结束）。

### RC3（＝G3）schema 校验只挂在 Pass4b，其它 Pass 放行未声明工具 —— Symptom B 伪调用

`validateBareArgs`（830-842，`some()` 在 841）**只在 Pass4b 对称裸标签里被传入**（939）。Pass3b（888-891）、Pass3（877-881）、Pass4（894-908）、Pass5（944-973）、Pass7（982-1000）的 `pushCall` 均未传 `validate`。因此在已声明 schema 的会话里：

- `<tool_call:delete_file>{"Path":"d:\\x.ts"}</delete_file>`（未声明工具 `delete_file`）→ Pass3b 命中 → 产出 `delete_file` functionCall；随后 `normalizeToolArgs` 会把未声明参数 `Path` 强转为 `AbsolutePath`（[Utils] 日志），IDE 以 `invalid tool call` 中止整轮。

### RC4（＝G4）代码围栏只在 Pass4b 检查 —— Symptom B 伪调用（引用示例误报）

`insideCodeFence`（925-928）只被 Pass4b（938）使用；Pass3/3b/4/5/7 不检查围栏。于是标注为代码示例的 ```` ``` <tool_call:list_dir>{json}</list_dir> ``` ```` 会被 Pass3b/4 解析成真实调用（e4 固化），同样触发 `invalid tool call`。

### RC5（＝G5）流式 `function_call` 未收口 —— 丢 native 调用 + 上下文残留

非流式 `finishReasonMap`（1117-1124）明确认识 `function_call → STOP`；但流式 native 收口（1341）**只在 `finish_reason==='tool_calls'`** 执行。`finish_reason==='function_call'` 时既不到 1259（stop/length）、也不到 1341（tool_calls），落到 1376-1380：`emitParts` 为空 → **返回 null（丢调用）**；且 `activeStreamContexts.delete` 只发生在 1223 / 1293 / 1322 / 1332 / 1372，`'function_call'` 不在其中 → **上下文残留（f5 断言 size===1）**，污染后续同 id 流。

### RC6（＝subtask 3 的“两类模型互相踩踏”）—— 边缘但确证的次因

`getLeanToolNames`（586-590）在 `modelToolNames.get` 为空时**回退到 `BUILTIN_LEAN_TOOL_NAMES`**（555-574）；`modelToolSchemas.get`（1177）此时为 null。`validateBareArgs` 在 `paramSchemas===null` 时**直接 return true**（831）。后果：若某会话未注册工具（或 30min TTL 清理后，`shared.ts:130-141`），**块边界处任何 `Buffer<view_file>` 引述都会被合成工具调用**，是“两类模型互相踩踏 → invalid tool call”的实锤。属次因 / 边界条件，非主路径，建议作为加固项处理。

### RC7（＝subtask 3 的 b/c 判定）—— sessionId 隔离与残留字段

- **b（隔离）**：`streamInstanceId = model|sessionId|Date.now-rand`（`proxy.ts:541`，传出为 `streamKey`，`openai.ts:1150` 优先）→ **流内累积文本已按连接隔离**，无串扰。但**跨轮**的工具名/schema/`toolCallIds`/`modelReasoningContent` 用 `stateKey(modelName,sessionId)`（`shared.ts:57-59`）。**有 sessionId 时隔离**（openai.test.ts:288 有专门用例）；**缺 sessionId 时退化为仅 `modelName`**（`stateKey` 59 行），并发同模型会话会互相覆盖 `modelToolCallIds` → 上游 400 `tool_use_id not found`。即：**流内隔离已正确，跨轮隔离只对“带 sessionId”的场景成立**。
- **c（残留字段）**：`emittedLen`（`shared.ts:17`）已声明却从未读写 → 死字段；`hasUnclosedBareToolBlock`（234）与 `isBlockBoundaryAndNotFenced`（261）同样死代码；`pendingHeldSuffix`（15）**非死**（被 1211/1213/1328-1330 使用）。三者确认为「还原流式发射」重构后的遗留。

## 四、哪个分支让 IDE 过早收到 STOP（Symptom B 直接触发器）

**finish 分支 1258-1338 的收尾 return（1333-1337）**：

```ts
1333  return {
1334    content: { parts: emitParts, role: 'model' },
1335    finishReason: finishReason === 'length' ? 'MAX_TOKENS' : 'STOP',
1336    index: 0,
1337  };
```

当 `finish_reason==='stop'` 且 pending native（1263）与 accumulated 文本解析（1298）都为空时，会给出 **`parts` 可能为空 / 只含泄漏文本 + `STOP`**。这正是 a2 复现的现象：流以 `STOP` 结束、无 functionCall，IDE 认为模型“已完成回答”，不再执行本应发生的工具调用 → 语义上的“提前结束”。

次要触发器：`hasEmittedToolCall` 抑制分支（1221-1226）把 finish 帧吞掉返回 null，属“防二次调用被取消”的保护，**不是**问题根源。

## 五、最小修复方案

按“改一行/一个小函数，能同时消掉多个根因”的原则排序。**不建议重写解析器，只做接线与正则收紧。**

1. **接线裸标签扣留（治 RC1/G2/G6，Symptom A）**
   - 在 `hasUnclosedToolCallBlock`（208-228）内追加裸工具名开闭计数：对 `leanToolNames`（传入）逐一统计 `<name>` / `</name>`，任一 `opens>closes` 返回 true；并让 `tcOpens`（213）/`fcOpens`（217）用 `/<(?:tool_call|function_call):?[>\s]/` 兼容冒号形式。
   - 把已存在的 `hasUnclosedBareToolBlock`（234）与 `isBlockBoundaryAndNotFenced`（261）真正接入：在 1179 用 `hasUnclosedBareToolBlock(prevAcc, leanToolNames)` 加入 `alreadyInsideToolBlock` 判定；在 1187-1192 的 marker 扫描里把 `leanToolNames` 生成的裸标签（`<name>` 前缀）也作为 marker 参与 `earliestIdx` 计算，避免 1194 整段放行。

2. **Pass5 认可冒号形式的未闭合块（治 RC2/G1，Symptom B 主因）**
   - 把 946 的 `unclosedRegex` 改为 `/<(?:tool_call:?|function_call:?)([A-Za-z_]\w*)>([\s\S]+)$/g`（同时兼容 `<tool_call>`、`<tool_call:name>`），使 `<tool_call:list_dir>{json}`（无闭合）在 `allowUnclosed=true` 的 finish（1298）被回收为 functionCall。注意此改动需与 pass3b 的正确匹配保持一致，避免被 Pass3b 抢先消费。

3. **`validateBareArgs` 扩散到所有边界候选 Pass（治 RC3/G3，Symptom B 伪调用）**
   - 给 `pushCall` 加默认校验（或在 Pass3b/3/4/5 调用时统统传 `validateBareArgs`），使**未声明工具名**在 schema 会话下被拒绝并落入 `cleanText` 保留原文，而非合成调用。

4. **代码围栏检查前移到最先命中的 Pass（治 RC4/G4，Symptom B 伪调用）**
   - 让 `insideCodeFence(idx)`（925）在 Pass3/3b/4/5/7 的匹配起点上同样生效：围栏内的 `<tool_call:...>{...}</...>`、`<run_command>{...}</run_command>` 一律视为示例文本，不解析为调用。

5. **流式 `function_call` 纳入收口 + 清理上下文（治 RC5/G5）**
   - 把 1341 的收口条件由 `finishReason === 'tool_calls'` 扩展为 `finishReason === 'tool_calls' || finishReason === 'function_call'`，并在该分支保留 `activeStreamContexts.delete(streamId)`（1372）。同时考虑让 1259 的 `stop/length` 分支也能对 `function_call` 做 pending native 收口。

6. **（加固，非必需）schema-null 时不回退裸标签解析（治 RC6）**
   - 当 `modelToolSchemas.get` 为 null 且 `modelToolNames.get` 为空（会话未声明工具）时，`getLeanToolNames` 不再用 `BUILTIN_LEAN_TOOL_NAMES` 兜底去解析裸标签，避免块边界引述被踩踏成伪调用；仅在“代理中重启、确需尽力恢复”时回退。需权衡误报与漏调，建议作为选项而非默认。
